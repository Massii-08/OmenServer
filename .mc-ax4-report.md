# Rapport — MC-Agent, run `world_ax4`

## Résumé en une phrase

**Le mur de la fonte est tombé** (première armure fer de l'histoire du projet : 3 pièces sur 4
portées), mais le run a plafonné sur un goulot qui n'est **ni le combat ni la fonte** : les bots
ont passé leur vie à chercher du bois qu'ils avaient eux-mêmes épuisé, en retournant **2036 fois
dans la même cellule déboisée**.

## 3. Le bug le plus coûteux du run : la boucle du bateau

**87 % de tous les events du run** viennent d'une seule boucle folle chez les cartographes :

```
mapper_boat_cross   115 384
mapper_boat_failed  115 342   dont no_crossable_water : 115 138
```

Les deux compteurs sont quasi identiques : **chaque tentative de traversée échoue, et le bot
recommence immédiatement, sans aucune temporisation**. Une seule session en compte 40 490.

Conséquences : les cartographes ne cartographient plus pendant ces phases, ils brûlent du CPU sur
l'Omen (et donc pénalisent les ouvriers), et ils ont généré **206 Mo de logs**.

C'est le correctif n°1 évident : un `no_crossable_water` doit poser un temps d'attente et
réorienter la frontière, pas relancer la même décision en boucle serrée.

## 4. Les trois blocages restants, par impact

### 4.1 — Le bois (bloquant absolu)

`directedTarget` choisit la cellule boisée la **plus proche**, sans mémoire de ce qui y a été
récolté. Avec 3 bots sur la même zone, cette cellule est vide en une heure et le reste.

Pistes : compter les récoltes par cellule et l'exclure au-delà d'un seuil ; préférer une cellule
boisée **jamais visitée** dès le 2ᵉ `not_found` consécutif ; ou planter des saplings (les bots en
ramassent déjà en cassant les feuilles).

### 4.2 — La nourriture

`no_prey` ×387, même pathologie : la faune locale est chassée puis ne revient pas. 4 morts de
faim, et surtout des bots qui perdent leur temps sur un but insatisfiable.

### 4.3 — NethBot3, cassé depuis le début

33 sessions, **zéro recette fer débloquée**, bloqué sur `logs`/`food_stock` de la première à la
dernière minute. Ses deux collègues sont partis du même spawn avec le même code. C'est donc
reproductible, et probablement le même problème de bois vu depuis le pire point de départ.

## 5. Ce que ce run apprend sur la méthode

- **Trois fausses alertes « les items ont disparu »** en une soirée. `data get entity` est
  tronqué sur Paper, `clear` ne renvoie rien via RCON, et le NBT brut mélange l'inventaire avec le
  livre de recettes. Le seul compteur fiable est celui que le bot publie lui-même (`worn`).
- **Recycler la flotte pour déployer coûte cher** : 5-6 recyclages en 90 minutes ont interrompu
  autant de progressions. Il faut grouper les correctifs et laisser des fenêtres franches.
- **`KillMode=process`** (posé ce soir) rend enfin les deploys inoffensifs pour la flotte — prouvé
  en direct : PIDs intacts après un `systemctl restart`, sessions ré-adoptées.
- **Mesurer avant de coder a payé deux fois** : l'alerte « 4065 faux réflexes de noyade » n'était
  qu'un cumul multi-sessions dominé par les cartographes (comportement normal), et l'alerte « plus
  aucun arbre » venait d'une boîte de mesure mal placée (960 blocs de feuillage juste au-dessus).

## 6. Ordre de bataille pour le prochain run

1. **Temporiser la boucle bateau** des cartographes (87 % des events, coût CPU réel).
2. **Mémoire de récolte par cellule** : ne pas renvoyer un bot sur une cellule qu'il a vidée →
   c'est le déblocage du bois, donc de la fonte, donc de l'armure.
3. **Nourriture** : même exclusion pour les zones chassées, et rendre `food_stock` non bloquant.
4. Reprendre le run sur un monde neuf **ou** déplacer le spawn de plusieurs centaines de blocs
   pour repartir sur une forêt intacte.
