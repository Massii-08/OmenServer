## Architecture livrée (mergée sur main, déployée)

```
3× MapperBot (objectif mapper)                    3× ResBot (objectif resource + quota)
   marche aléatoire persistante (sectors)            boucle: claim → goto borné → mine borné
   scanAllOres (256 blocs, 5 types quota,            quota.js: have = banked + inventaire
     exposés ET enfouis, flag exposed)               claims.js: claims-<group>.json TTL 120s
   émission BATCHÉE ores_found                       reload mémoire LIVE (--wm-live)
        ↓ stdout events                                   ↓↑ lecture seule + events
   backend manager (_WM_EVENTS) ────────→ data/mc_agent_world_memory/8d91a7.json
   add_ore cap 800 PAR TYPE                       worlds[overworld].ores=[{material,x,y,z,exposed}]
        ↓                                              ↓
   GET /servers/{sid}/memory ──→ carte canvas (carrés colorés par type, plein=exposé)
   quota_progress events ──→ session.quota ──→ /active ──→ barres par bot (Multi-bot)
```

## Problèmes trouvés grâce au parallélisme (but de la mission)

1. **Éviction des diamants par le fer** (cap global FIFO) → cap par type. Sans 3 mappers
   simultanés, le flot de fer n'aurait pas saturé le cap aussi vite.
2. **Freeze infini `collectBlock`** (ResBot1) — le goto était borné, pas le collect final.
3. **Symlink node_modules absolu Mac committé sur main** → prod mc-agent cassée depuis le
   5/6 20:10 (tout lancement de bot aurait crashé). Purgé + npm install.
4. Throughput : cibles profondes (y≈0-10) = minutes de tunnel par ore ; la priorité diamant
   d'abord concentre la friction au début du run (assumé : denrée la plus rare d'abord).
